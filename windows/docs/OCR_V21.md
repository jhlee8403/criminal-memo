# OCR v2.1 최종 비교 결과

이 수치는 저장소 공소장 2개와 그 자료에서 만든 합성 변형 8개, 총 **10문서**에서 단회 측정한 결과입니다. 독립적인 실제 회사 공소장 표본이 아니며 일반 인식률로 해석하면 안 됩니다. Linux Chromium 메모리 HTML 진단입니다. **실제 Windows Edge file://는 미검증**입니다.

## 정확도와 확인 보류

자동 정답은 검토 화면에 자동 선택한 값이 기준 정답과 완전히 일치한 경우입니다. 보류는 빈 최종값/충돌/사용자 확인 필요이며 오답과 구별합니다. 후보 포함은 노출된 후보 중 정답이 있는 경우입니다. 구버전은 자동값 하나를 노출 후보로 간주합니다. 모든 PDF 생성에는 별도의 원문 대조 확인이 필요합니다.

## 처리 비용

10문서 분석 합계: 기존 **19.34초**, 개선 **51.78초**. OCR 호출 합계 **5 → 55회**. 정밀 비교로 비용이 늘었습니다. 문서별 초기화·페이지 처리까지 포함하며 반복 실험의 통계적 평균/상한이 아닙니다.

- before: 분석 완료 후 renderer 프로세스 RSS 합계 스냅샷 353~686 MiB.
- after: 분석 완료 후 renderer 프로세스 RSS 합계 스냅샷 376~759 MiB.

RSS는 Linux에서 테스트 브라우저의 renderer 프로세스들을 더한 **완료 후 스냅샷**입니다. 작업 중 최고값/전체 브라우저+WASM 메모리/개별 문서의 증분 메모리를 뜻하지 않습니다. JS heap API는 근사값이며, 이미지 메모리 추정도 진단 JSON에 별도 기록했습니다. 전체 최대 RSS를 보장하지 않습니다.

## 전체 OCR·영역 OCR 및 설정 비교

정상 문서와 기울어진 문서의 주석 영역에서 원본·그레이·대비·적응형 이진화·기울기/노이즈 처리, PSM 3/6/7/11, kor/kor+eng를 비교해 **32건**을 실행했습니다. 주석 영역은 시험의 정답 위치이며 제품에 고정 좌표로 넣지 않았습니다.

- 정상 검사 이름과 죄명은 짧은 영역에서 PSM 7/6으로 정답을 찾았지만 PSM 3에서는 후보가 없는 경우가 있었습니다.
- 기울기/노이즈 문서에서는 전체 자동 탐색이 실패해도 올바른 수동 주석 영역에서 이름·죄명을 찾았습니다.
- 적응형 이진화는 일부 이름 인식 결과를 오히려 잃었습니다. kor 전용이 항상 더 좋지도 않았습니다.
- 첫 OCR 호출은 Worker 초기화를 포함하므로 방법 간 소요시간을 그대로 속도 순위로 비교하면 안 됩니다.

실제 혼합 시험에서는 원본 영역 OCR의 `상해`가 신뢰도 59인 반면 대비 처리의 `상헤`는 84였습니다. 높은 점수를 정답으로 고르지 않고 두 후보를 검토 대상으로 남겼습니다.

## 실패·한계

- 90DPI 스캔, 자동 영역 탐색에 실패한 기울기/노이즈 문서는 정답 후보가 없거나 부족했습니다. 확대가 손실된 정보를 복원하지 못합니다.
- 작은 글씨 시험과 잘못된 선택 가능 텍스트 시험에서는 검사 후보를 찾아도 죄명 전체를 정확한 별도 목록으로 복원하지 못한 경우가 남았습니다.
- 의미가 불명확한 죄명 줄바꿈은 임의로 합치거나 쪼개서 확정하지 않고 확인을 요구합니다.
- 같은 엔진의 전처리 결과가 일치해도 참임을 보장하지 않습니다. 원문 대조가 필요합니다.
- 실제 새로운 불량 공소장 표본은 제공되지 않았습니다. 이 시험만으로 일반 인식률·실제 모든 양식의 성공을 보장하지 않습니다.
